I. Foundations What an agent actually is
01

Anatomy of an agent

LLM + tools + a loop that controls context. Three responsibilities; one of them is invisible.

An agent has three components and one job each:

  • LLM — decide the next action.
  • Tools — act on the world (read, write, fetch, call APIs).
  • Loop — manage context, decide when the task is done, recover when something breaks.

Engineers fixate on the first two. The loop is where production agents fall apart. Most of this playbook is about the loop.

The four hidden responsibilities of the loop

  1. Decide what the model sees each step (input gating).
  2. Decide when the loop ends (stop conditions).
  3. Decide how the loop survives failures (recovery).
  4. Decide what gets persisted between sessions (memory).
Mental model
The model is a stateless function from (system, messages, tools) to (text | tool_call). Everything else — cache, history, memory, retrieval — is your job. The "agent" abstraction is just code around that function.

Three callbacks own everything: stopWhen, prepareStep, onStepFinish.

The AI SDK loop runs each step: model call → tool calls (if any) → tool results → back to the model. It stops when:

  • The model emits text without a tool call.
  • A stopWhen condition fires.
  • A tool has no execute (you handle it client-side).
  • A tool needs approval.
import { streamText, stepCountIs, hasToolCall } from 'ai';

const result = streamText({
  model,
  system,
  messages,
  tools,

  // 1. when to stop — compose freely
  stopWhen: [stepCountIs(20), hasToolCall('finish'), budgetGuard],

  // 2. per-step lever — change anything before each step
  prepareStep: async ({ stepNumber, steps, messages }) => {
    if (messages.length > 40) {
      return { messages: [messages[0], ...messages.slice(-20)] };
    }
    return {};
  },

  // 3. observe and persist — runs after each step
  onStepFinish: ({ stepNumber, text, toolCalls, toolResults, usage }) => {
    saveStep(stepNumber, { text, toolCalls, toolResults });
    trackUsage(usage);
  },
});

ConditionWhy
stepCountIs(N)Always. Hard ceiling against runaway loops.
budgetGuardStop if cumulative usage > $X. Cheap insurance.

verifyCleanDon't let the model "finish" while lint/tests fail. See §5.

A custom StopCondition is just ({ steps }) => boolean. Sum usage across steps, multiply by price, return true if > budget. Done.
II. Tools The agent's hands

Tool design

Few, narrow, well-described. The description is part of the prompt; the schema is your validation.

import { tool } from 'ai';
import { z } from 'zod';

const readFile = tool({
  description: 'Read a UTF-8 file. Returns content with line numbers prefixed (1-indexed).',
  inputSchema: z.object({
    path: z.string().describe('relative path from workspace root'),
    startLine: z.number().nullable().describe('1-indexed; null for start of file'),
    endLine: z.number().nullable().describe('1-indexed inclusive; null for end of file'),
  }),
  execute: async ({ path, startLine, endLine }) => {
    // always return a Result — never throw for expected failures
    return readFileImpl(path, startLine, endLine);
  },
});

Rules of thumb

  • Keep tool count low — 5 or fewer for weaker models, ≤15 even for strong ones.
  • .describe() every field. The schema is read by the model.
  • Use .nullable(), not .optional() — strict-mode providers reject optional fields.
  • Avoid deeply nested unions in schemas. Models fail at them.
  • Set temperature: 0 for tool-heavy workflows.
  • Name tools semantically: readFile > fileOp. The name is a prompt.
  • Advertise idempotency in the description: "Cached for 15 minutes." Prevents redundant calls.
Return a Result envelope
A discriminated union: {ok:true, data} | {ok:false, error:{code, message, hint}}. Tool errors become next-step reasoning fuel.
Throw on expected errors
Throwing inside execute for things you expect to happen (file not found, validation fail) kills the turn. Results steer it.

The Result envelope

type Result<T> =
  | { ok: true; data: T; warnings?: string[] }
  | { ok: false; error: { code: string; message: string; hint?: string } };

Throw only when the infrastructure is broken (disk error, OOM). Use {ok:false} for everything the model can recover from.

Errors & steering

Every error message is a prompt. Write it like one.

The model's next action is shaped by what your error said. Prescriptive errors recover; vague errors loop.

"Invalid input"
"Error 500"
Steering (the model knows the next move)
"Found 3 matches but replace_all is false. To replace all, set replace_all: true. To replace one, provide more context to make the string unique."

The "Did you mean…" pattern

On any not-found error, compute the nearest match and offer it. Costs nothing, prevents retry death-spirals.

When the model emits a malformed tool call (wrong schema), the AI SDK can repair it with a side LLM call instead of wasting a turn:

05

Self-correction loops

Generate → evaluate → regenerate. Bound the iterations. Inject the feedback.

The evaluator-optimiser pattern. Run an LLM, judge its output with another (structured) LLM, regenerate with feedback if quality is low. Bound by max-iterations.

async function withFeedback(prompt: string) {
  let output = await generate(prompt);

  for (let i = 0; i < 3; i++) {
    const { object: evaluation } = await generateObject({
      model,
      schema: z.object({
        score: z.number().min(1).max(10),
        issues: z.array(z.string()),
        suggestions: z.array(z.string()),
      }),
      prompt: `Evaluate against criteria X, Y, Z:\n${output}`,
    });

    if (evaluation.score >= 8) break;

    output = await generate(`Improve based on:\n${evaluation.issues.join('\n')}\n\nOriginal:\n${output}`);
  }

  return output;
}

The "verify before stop" pattern

For agents that do destructive work (code edits, data changes), make a custom StopCondition that refuses to let the agent finish if verification fails. Combine with an injected reminder so the next step has the feedback.

const verifyClean: StopCondition<typeof tools> = ({ steps }) => {
  const lastBuild = steps.findLast(s =>
    s.toolCalls?.some(c => c.toolName === 'build'));
  const errors = lastBuild?.toolResults?.[0]?.output?.errors ?? [];
  return errors.length === 0; // stop only if clean
};

// Combined with prepareStep that injects the build errors as feedback:
prepareStep: async ({ steps, messages }) => {
  const errors = latestBuildErrors(steps);
  if (errors.length && lastMessageIsAssistantTryingToStop(messages)) {
    return {
      messages: [...messages, {
        role: 'user',

      }],
    };
  }
  return {};
}
Gotcha
Every retry loop needs a counter cap. Claude Code documented "1,279 sessions had 50+ consecutive failures, wasting ~250K API calls/day" before they added MAX_CONSECUTIVE_FAILURES = 3. Bound everything.

What belongs in the static prefix

  • Tone rules — how to respond, response length, format.

The <system-reminder> envelope

A wrapper convention that lets you speak to the model in the user role. Teach it once; use it everywhere.

<system-reminder> is not an API feature. It's a wrapper tag you put around any text that should feel system-spoken — even though it arrives in the user role. The model must be taught what it means.

export function wrapInSystemReminder(content: string): string {
  return `<system-reminder>\n${content}\n</system-reminder>`;
}

Teach it in the system prompt

Tool results and user messages may include <system-reminder> tags. <system-reminder> tags contain useful information and reminders. They are automatically added by the system, and bear no direct relation to the specific tool results or user messages in which they appear. Claude Code constants/prompts.ts

Now you can inject context into the conversation without bloating the system prompt (which should stay cacheable) and without confusing it with real user input.

Auto-injection

Don't re-send snapshots. Send deltas — what changed since last turn.

If the file tree has 200 entries and 3 changed, re-sending all 200 wastes context and busts cache. Track what was last announced; send only the diff.

interface SessionState {
  announcedFiles: Set<string>;        // what we told the model exists
  fileStateCache: Map<string, FileState>; // last-read content + mtime
  lastToolUseTurn: Map<string, number>;  // for cadence reminders
  pendingHooks: HookContext[];          // PreToolUse → next-turn injection
}

// Each turn, compute deltas:
function buildAttachmentsForTurn(state: SessionState, current: WorldState) {
  const attachments: Attachment[] = [];

  // New files since last turn
  const newFiles = current.files.filter(f => !state.announcedFiles.has(f));
  if (newFiles.length) {
    attachments.push({ kind: 'new_files', paths: newFiles });
    newFiles.forEach(f => state.announcedFiles.add(f));
  }

  // Files modified since last announced
  for (const [path, cached] of state.fileStateCache) {
    if (currentMtime(path) > cached.mtime) {
      attachments.push({ kind: 'file_changed', path });
    }
  }

  return attachments.map(a => wrapInSystemReminder(formatAttachment(a)));
}

Cadence reminders

Some reminders fire on cadence, not events. Example: nudge the model to use a task list every N turns of complex work.

const TODO_REMINDER = `The TodoWrite tool hasn't been used recently. If you're working on tasks that would benefit from tracking progress, consider using the TodoWrite tool to track progress. Also consider cleaning up the todo list if it has become stale and no longer matches what you are working on. Only use it if it's relevant to the current work. This is just a gentle reminder - ignore if not applicable. Make sure that you NEVER mention this reminder to the user`;

const TURNS_SINCE = state.lastToolUseTurn.get('TodoWrite') ?? 0;
const TURNS_BETWEEN = 10;

if (currentTurn - TURNS_SINCE >= TURNS_BETWEEN) {
  attachments.push(wrapInSystemReminder(TODO_REMINDER));
}

File-state cache — the single biggest context win

Keep a per-session Map<path, {content, mtime, offset, limit}>. On read_file:

  • If mtime unchanged and content cached → return a stub: "File unchanged since last read. Refer to the earlier tool result."
  • If mtime changed → serve fresh, update cache.
  • On edit_file success → update cache with new content.

Anthropic's reported impact in one window: 1,734 dedup hits in 2 hours, no regression. This is the cheapest high-impact change you can make.

Compaction

Three tiers: slice old messages, clear old tool results, summarise. Re-inject state. Bound failures.

Eventually the conversation exceeds the context window. You either compact gracefully or the agent dies.

Trigger from tokens, not message count

const COMPACT_BUFFER = 13_000; // reserve for summary output
const EFFECTIVE_CTX = contextWindow - Math.max(maxOutputTokens, 20_000);
const THRESHOLD = EFFECTIVE_CTX - COMPACT_BUFFER;

if (estimateTokens(messages) > THRESHOLD) {
  await compact(messages);
}

Tier 3: the summary prompt — the gotcha

CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.

The 9-section summary template

  1. Primary request and intent
  2. Key technical concepts
  3. Files and code sections (with paths)
  4. Errors and fixes
  5. Problem solving (decisions made)
  6. All user messages, verbatim (the model writes terribly without this)
  7. Pending tasks
  8. Current work (in progress)
  9. Optional next step

Rolling window summary — continuous compaction

Autocompact fires once, near the context ceiling, with a single expensive summary call. The rolling window pattern is the opposite: a small, continuous summary that's always present and absorbs old turns incrementally. Best for long-lived chat agents (support bots, companions, copilots) where conversations span hours and the autocompact "bang" creates a noticeable hiccup.

The algorithm

const WINDOW_SIZE = 20;       // turns kept verbatim
const COMPACT_EVERY = 4;      // fold every N turns into summary

prepareStep: async ({ messages }) => {
  const turns = countTurns(messages);
  if (turns <= WINDOW_SIZE) return {};

  const overflow = turns - WINDOW_SIZE;
  if (overflow % COMPACT_EVERY !== 0) return {};  // only on cadence

  // Fold the oldest COMPACT_EVERY turns into the running summary.
  const [system, ...rest] = messages;
  const [runningSummaryMsg, ...history] = extractRunningSummary(rest);
  const toFold = history.slice(0, COMPACT_EVERY);
  const recent = history.slice(COMPACT_EVERY);

  const { text: updated } = await generateText({
    model: 'claude-haiku-4-5',
    system: 'You maintain a running summary of an ongoing conversation. Update the summary to absorb the new turns. Preserve named entities, open threads, decisions made. Keep under 800 tokens.',
    prompt: `Current summary:\n${runningSummaryMsg.content}\n\nNew turns to absorb:\n${format(toFold)}`,
    temperature: 0,
  });

  return {
    messages: [
      system,
      { role: 'user', content: wrapInSystemReminder(`Conversation summary so far:\n\n${updated}`) },
      ...recent,
    ],
  };
}

Rolling vs autocompact — when to use which

Rolling window
  • Long-lived chat agents (support, companion, copilot)
  • Conversations span hours or days
  • Cost smoothed across turns
  • No "compact pause" hiccup
  • Continuous information loss (small at any moment)
Autocompact (one-shot)
  • Bursty work (coding sessions, research dives)
  • Most sessions never hit the limit
  • Pays for compaction only when needed
  • Concentrated information loss at the boundary
  • Lower total LLM spend for short sessions
You can combine them
Run a rolling window during normal operation; let autocompact catch the edge cases where the window plus the running summary still overflow. The rolling pattern lowers when autocompact fires, not whether.

Level 2 — loop recovery

Withhold transient errors from the consumer until recovery is attempted. The user shouldn't see "context too long" if you can compact and continue.

try {
  return await runStep();
} catch (err) {
  if (isPromptTooLong(err)) {
    await compact();                  // recover
    return await runStep();         // retry once
  }
  if (isMaxTokensHit(err)) {
    messages.push({
      role: 'user',
      content: wrapInSystemReminder('Output token limit hit. Resume directly — no apology, no recap of what you were doing. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.'),
    });
    return await runStep();
  }
  throw err;  // only now does the user see it
}

Level 3 — tool errors as feedback

Tool throws should become tool_result with is_error: true, not propagate to the loop:

try {
  const output = await tool.execute(input);
  return { type: 'tool_result', content: output };
} catch (err) {
  return {
    type: 'tool_result',
    is_error: true,
    content: `<tool_use_error>Error calling tool ${tool.name}: ${err.message}</tool_use_error>`,
  };
}

Conversation well-formedness

Every tool_use block in your message history must have a paired tool_result. On any catch/abort, sweep dangling uses and inject synthetic results:

function yieldMissingToolResults(state) {

Loop control

A state machine with a transition field. Every continue is an explicit state replacement.

For agents beyond the basic streamText wrapper, write the loop as a state machine. Tag every continuation with why. Then your logs explain themselves.

type Transition =
  | 'completed'
  | 'aborted_streaming'
  | 'aborted_tools'
  | 'budget_hit'
  | 'prompt_too_long'
  | 'max_turns'
  | 'hook_stopped'
  | 'compacted_and_retrying'
  | 'recovered_max_tokens';

async function* queryLoop(initial: State) {
  let state = initial;

  while (true) {
    yield { type: 'stream_request_start' };

    const result = await runStep(state);

    if (result.transition === 'completed') return;
    if (result.transition === 'budget_hit') return;
    if (state.turn >= MAX_TURNS) return;

    state = result.next;
  }
}

For agents that run on a schedule or watch for events, teach the model to detect its own idleness. Don't let it tick out useless text:

The five must-haves

  1. Server-side message IDs. Stable across reload; lets the client splice retries instead of duplicating.
    generateMessageId: createIdGenerator({ prefix: 'msg', size: 16 })
  2. Pre-flight save of user turn. Before calling the model. A provider failure can't lose the user's words.
  3. Validation on load. Tools change schemas; old transcripts break otherwise.
    validateUIMessages({ messages, tools, metadataSchema }) → catch TypeValidationError → fall back to [] or migrate.
  4. Client sends only the latest message. Server loads history, splices, runs.
    prepareSendMessagesRequest({ messages, id }) => ({ body: { message: messages.at(-1), id } })
  5. Keep server alive on disconnect. Call result.consumeStream() (no await). Stream finishes, onFinish saves, even if the browser tab closed.

The route handler in 12 lines

export async function POST(req: Request) {
  const { message, id } = await req.json();
  const previous = await loadChat(id);
  const messages = await validateUIMessages({ messages: [...previous, message], tools });

  await saveChat({ chatId: id, messages });  // pre-flight

  const result = streamText({
    model, system, tools,
    messages: await convertToModelMessages(messages),
  });
  result.consumeStream();  // no await — keeps server draining

  return result.toUIMessageStreamResponse({
    originalMessages: messages,
    generateMessageId: createIdGenerator({ prefix: 'msg', size: 16 }),
    onFinish: ({ messages: final }) => saveChat({ chatId: id, messages: final }),
  });
}

Before persisting, ensure no tool_use is dangling. Either pair every use with a result (real or synthetic) or you'll fail API validation on resume.

Awareness

The agent must know it has memory, that compaction happens, that some context is volatile. Teach this.

Saving etiquette

Memory grows; quality matters. Train the model to be selective:

Filesystem RAG

Chunking strategies

Too small loses context, too large loses precision. Seven strategies, ranked by sophistication.

The fundamental failure mode

Why naive chunking breaks retrieval 
Original document:
"Berlin is the capital of Germany. The city has 3.8M people..."

Naive chunk on "." boundary:
  C1: "Berlin is the capital of Germany."
  C2: "The city has 3.8M people..."

Query: "What is Berlin's population?"
  ↓
  similarity matches C2 (population, city)
  ↓
  C2 retrieved — but "the city" never resolves to "Berlin"
  ↓
  Model hallucinates or asks "which city?"

Seven strategies

Chunking strategies, by sophistication
1
Fixed size
N tokens or chars. Simple, lossy at boundaries. Always overlap 10–20%.
2
Recursive character splitting
Split by paragraph → sentence → word until under size. LangChain default. Solid baseline.
3
Semantic chunking
Break where adjacent sentence embeddings diverge. Better boundaries; expensive at index time.
4
Hierarchical / parent-child
Index small chunks (retrieval precision); inject parent chunk or section (context). "Small-to-big."
5
Contextual chunking (Anthropic)
LLM writes 50–100 token context blurb per chunk. Prepend before embedding AND BM25 indexing. -49% retrieval failure (-67% with reranker).
6
Late chunking (Jina)
Embed entire doc first with long-context model. Pool token embeddings into chunks afterward. Each chunk vector carries cross-chunk context "for free."
7
Agentic chunking
LLM decides boundaries. Most expensive. Worth it for legal contracts, regulatory docs, anything with implicit hierarchy.

Reranking

Retrieval finds candidates (recall). Reranker scores them (precision). Two-stage is non-negotiable.

Vector similarity has high recall but mediocre precision past top-10. Cross-encoders trade speed for accuracy — perfect for scoring a small candidate set.

Bi-encoder vs cross-encoder

Bi-encoder (retrieval)
encode(query) → q
encode(doc)   → d
score = cos(q, d)
  • Each encoded once, independently
  • Cacheable, indexable
  • Lossy — no query/doc interaction
  • Fast: ms per query over millions of docs
Cross-encoder (reranker)
encode(query, doc) → score
(jointly attend)
  • Encoded together; full attention
  • Per-pair compute — cannot pre-index
  • High precision
  • Slow: ~10–100ms per pair

Beyond cross-encoders

  • MMR — Maximal Marginal Relevance. Rerank for diversity. Avoid returning five near-duplicates when the top-5 vectors all came from the same doc. score = λ·rel(q,d) − (1−λ)·max sim(d, selected).
  • LLM scoring with rubric. Pass top-K to a fast model with a structured scoring prompt. More expensive than dedicated rerankers but lets you encode arbitrary criteria.
  • Cascade rerankers. bge-small → bge-large → cohere-rerank-3. Each tier prunes more aggressively. Net cost lower than a single large reranker over the full top-K.

When to skip reranking

If the model has a 1M-token context and you can afford the inference cost, just stuff the top 50 into the prompt and let the model attend. The model is the cross-encoder. This is increasingly economical with Gemini 2.5 Pro / Claude Sonnet 4.6.

A · Filesystem + Vector

For agents over structured data and unstructured docs. One agent-facing search tool dispatches internally:

const search = tool({
  description: 'Search across records (structured) and docs (unstructured). Returns top matches with sources.',
  inputSchema: z.object({
    query: z.string(),
    scope: z.enum(['records', 'docs', 'all']).describe(
      'records=grep over filesystem, docs=vector search, all=both'),
  }),
  execute: async ({ query, scope }) => {
    const results = [];
    if (scope !== 'docs') results.push(...await fsGrep(query));
    if (scope !== 'records') results.push(...await vectorSearch(query));
    return await rerank(query, results, { topK: 8 });
  },
});

B · Sparse + Dense via RRF

The default for any general text corpus where queries mix exact-match and semantic. BM25 is a classic lexical scorer. Vectors are semantic. Neither is sufficient alone.

BM25 catches
  • Product codes, order IDs
  • Proper nouns, person names
  • Rare technical terms
  • Exact phrases users typed
Vectors catch
  • Paraphrases, synonyms
  • Conceptual similarity
  • Cross-lingual matches
  • Intent behind the words

Reciprocal Rank Fusion

Combining the two systems means combining their rankings. Score normalization is fragile (BM25 is unbounded; cosine is [-1,1]; outliers skew). RRF sidesteps the problem by using ranks, not scores.

RRF score for each doc = Σ 1 / (k + ranki), k ≈ 60. Higher rank in either system → higher fused score. Rank-based, so it's robust across heterogeneous scorers.

function rrf(rankings: Map<string, number>[], k = 60): Map<string, number> {
  const scores = new Map<string, number>();
  for (const ranks of rankings) {
    for (const [docId, rank] of ranks) {
      scores.set(docId, (scores.get(docId) ?? 0) + 1 / (k + rank));
    }
  }
  return scores;
}

// Usage:
const bm25Hits = await bm25Search(query, { topK: 50 });
const vecHits  = await vectorSearch(query, { topK: 50 });
const fused = rrf([toRanks(bm25Hits), toRanks(vecHits)]);
const reranked = await rerank(query, topN(fused, 20), { topK: 5 });

For PDFs where the visual layout encodes meaning — financial reports, scientific papers with figures, slide decks, forms. ColPali variants feed page images to a vision-language model and produce multi-vector embeddings via late interaction. No OCR step, no chunker, no layout-loss.

Text pipeline on layout-heavy docs

  • Tables become text spaghetti
  • Equations get mangled
  • Charts lost entirely
ColPali on the same docs
  • Page-as-image; ViT patches embedded
  • Late-interaction match at retrieval time
  • Layout, charts, figures all signals
  • Single end-to-end trainable model

Stream by default. Suppress errors into the stream (callers love that). Anti-flicker is a contract, not a hack.

The streamText error trap

streamText suppresses errors into the stream to avoid crashing servers. If you don't register onError, errors disappear silently:

const result = streamText({
  model, messages,
  onError: ({ error }) => logger.error({ err: error }, 'stream error'),  // REQUIRED
  onAbort: ({ steps }) => markAborted(steps),                                // distinct from onFinish
  onFinish: ({ messages: final, totalUsage }) => persistAndTrack(final, totalUsage),
});

Smoothing the stream

import { smoothStream } from 'ai';

const result = streamText({
  model, messages,

});

When you stop the stream early (step cap, guardrail trip, budget), you must emit synthetic finish-step and finish events or downstream code hangs:

experimental_transform: () => new TransformStream({
  transform(chunk, controller) {
    if (chunk.type === 'finish' && capWasHit()) {
      // Splice in a notice for the user before the natural finish
      controller.enqueue({ type: 'text-start', id: 'notice' });
      controller.enqueue({ type: 'text-delta', id: 'notice', delta: '\n\n…Reached the step cap. Ask me to continue.' });
      controller.enqueue({ type: 'text-end', id: 'notice' });
    }
    controller.enqueue(chunk);
  },
}),

The anti-flicker contract

For UIs that show server-derived status and let the user trigger mutations, optimistic updates flicker unless you do three things together:

  1. In-flight registry — track {kind, id} for every active mutation. beginMutation() / endMutation().
  2. Mask all error fields while mutating — not just status. lastError, dependencyError, anything that could contradict the loading state.
  3. Skip polling while mutations in flight — reschedule short (~400ms). Resume normal cadence when registry empties.
Why not useOptimistic?
The optimistic state vanishes the moment the startTransition callback returns; the network await happens outside the transition. Symptom: "see Cancel for a split second, then back to disabled Approve." Use plain useState + per-ID override map + poll reconciliation.

Production checklist

If you can't tick all of these, you're going to find out which one you needed at 3am.

Loop

  • stopWhen: stepCountIs(N) — hard ceiling.
  • A cost / budget stop condition.
  • prepareStep handles message-history slicing past a threshold.
  • onStepFinish persists every step.
  • Every tool_use has a paired tool_result on exit (including aborts).

Tools

  • ≤15 tools, narrow surfaces, every field has .describe().
  • Optional params use .nullable(), not .optional().
  • Errors return {ok:false, error:{code, message, hint}} instead of throwing.
  • "Did you mean…" suggestions on not-found errors.
  • Per-tool result size cap; persist overflow to disk and return a preview.
  • isReadOnly / isConcurrencySafe metadata on every tool.
  • experimental_repairToolCall registered.

Context

  • System prompt split into static + dynamic with a sentinel marker.
  • Anthropic cacheControl: 'ephemeral' on the static prefix.
  • Per-turn metadata in a prepended <system-reminder> user message.
  • Model is taught what <system-reminder> means.
  • File-state cache keyed on (path, mtime); returns dedup stub for unchanged files.
  • Attachments are deltas, not snapshots.

Survival

  • Compaction triggers from tokens, not message count.
  • Three tiers: slice → microcompact → summarise.
  • Summary prompt has TEXT ONLY preamble and trailer.
  • Post-compaction re-injection: files, plan, skills, deltas.
  • MAX_CONSECUTIVE_COMPACT_FAILURES = 3 circuit breaker.
  • Provider retry with exponential backoff + jitter, max 10 attempts.
  • Foreground vs background discrimination on 529.
  • Model fallback on repeated 529.
  • PTL / max-tokens errors withheld from caller until recovery exhausts.
  • Heartbeat yields during long waits (host idle-kill protection).
  • No stop-hooks on a failed turn.

Memory

  • UIMessage[] stored, not ModelMessage[].
  • Atomic write (tmp + rename) on save.
  • Server-side message IDs.
  • Pre-flight save of user turn before model call.
  • validateUIMessages on load with TypeValidationError fallback.
  • consumeStream() called (no await) to survive client disconnect.
  • Memory file format: frontmatter + body, index in MEMORY.md kept ≤200 lines.
  • Model taught about memory: what to save, what NOT to save, "ignore memory" override.

Retrieval

  • Structured data lives in a directory tree, not a vector DB.
  • Path traversal / symlink escape checks on every read/write.
  • OCR output is Markdown, not raw text. Tables, headings, lists preserved.
  • Source page index stored with every chunk; citations resolve to origin.
  • Embedding model name stored alongside every vector.
  • Chunks have a prepended header (source path, section, page); 10–20% overlap.
  • Two-stage retrieval: bi-encoder candidates → cross-encoder rerank.
  • For BM25 + vector hybrid: RRF (rank-based), not score fusion.
  • Re-index plan documented for when embedding model changes.
  • Vector retrieval used only where filesystem retrieval is genuinely insufficient.

UI & observability

  • onError registered on streamText (else silent failures).
  • onAbort distinct from onFinish.
  • Anti-flicker contract enforced where polling meets mutations.
  • Every API route has a request ID; logs are pre-bound with it.
  • Error envelopes are structured (code, message, retryable flag).

You don't need all of these on day one. You'll discover which one you skipped at the worst possible moment. Plan for which moment that will be.

IX. Hard-won Five laws, measured in shipped code
25

Absence is not a determination

Three outcomes need three values, and the unknown one is never the default. Found twelve times in eleven layers.

A boolean cannot carry yes, no, and we could not tell. Forced to, the third state collapses into whichever of the other two is cheaper to write — and that is almost always the reassuring one. Pass the error, not the absence of data, because null means two things.

Any encoding with fewer states than the data has is this defect. That includes visual encodings, which is where it is hardest to see, because no string is wrong.

Two states
A chart drew a reading with no reference range as a filled circle — identical to one confirmed in range.
Three states
In range, out of range, and unknown → dashed and unfilled. The third case now looks like what it is.
It arrives inside libraries you do not control
A disabled query reporting isPending: true is indistinguishable from one in flight — so a screen gated on another fetch renders a skeleton forever, with no exit. A dismissed dialog left mounted with data-closed means presence is not openness. When a third-party flag conflates "no information" with "no", derive the state you need instead of reading theirs.

The hardest sub-shape: a correct fail-closed normaliser, read by a second consumer

A normaliser mapping absent → unsupported is right for resolution, because unknown must fail closed. But ask it "did the record state a value?" and the answer can never be no — so "nothing given" and "explicitly unsupported" become one value, and a whole branch goes unreachable even with a correct fixture.

Nobody suspects code that is correct for its own purpose. Read the raw field when the question is whether something was stated.

Assume another instance exists
Every time we have looked, it has. Full treatment: lessons/01-thinking-framework.md.
26

Populations, not passes

A check states a property over a set. A green result is a claim about the set it reached — not about your system.

"40 of 40 routes observed" is true, and reads as more than it is. When a check passes, ask what it could not see.

Three instruments, three blind spots. Not a hierarchy:

String / AST sweep
Finds the sites you thought of. Blind to anything spelled differently — a single-line pattern cannot see a call that wrapped across lines. Found 13.
Gate over a derived population
Finds whatever its population reaches, which is always narrower than the name suggests. Found 8 more.
Opening the rendered result
Finds the rest. Slow, unrepeatable, no coverage claim. Found the one the other two structurally could not reach.

Three ways a population fails, each needing a different fix

  1. You measured the wrong artifact. A scan of server-rendered bytes on a client-rendered product saw 1 element where 37 rendered. The predicate was right; the population was a loading skeleton. Observe the real output, and refuse to fall back to the cheap proxy.
  2. An instrument page masked it. A component gallery renders everything, so it contributed 861 hits while real pages contributed one each. The instrument page hid the instrument's blindness. Same page, two jobs; trustworthy for one. Know which job you are doing.
  3. A dynamic route enters as one instance. One id per route shape means one instance is observable and the rest are not. Genuinely hard — enumerating instances makes the population hand-maintained again, which is what deriving it was for.
A check that cannot fail is not evidence
Two fallback tests were quietly satisfied by the authoritative source, so the leg under test never ran. "It returned the right answer" does not say which branch produced it. Split the I/O from a pure function over resolved inputs, so a higher-precedence source can be forced absent and proven absent in the same assertion.
27

Permissions, not prohibitions

You cannot enumerate the absences. A guard written as a blocklist is wrong by construction.

A guard derived by subtraction from a known vocabulary cannot drift. One written as a list of bad cases drifts the first time reality invents a new one.

A database trigger listing the blocked cases let a NULL match no clause and land in a gated table — allow-by-omission, which is ch. 25 again: a boolean standing in for three states, where the unhandled one is the reassuring answer. Inverted to name what is allowed and refuse the rest, it immediately surfaced a hole nobody had reported.

A negated character class is a blocklist — and it is the form nobody recognises as one

Listing what may not appear
/<\/strong>[A-Za-z]/
"the letters that may not follow a closing tag". Cancel— the link ships straight through: an em dash is not a letter.
Stating the property
A character may abut the tag only if it cannot begin the next word. The em dash fails without anyone having had to think of it.

Same class, twice more in the same file:

  • <[^>]+> to strip tags forgets that > is legal inside a quoted attribute — so alt="ratio > 1" ends the tag early and leaks markup into text you then treat as prose.
  • A negated class capturing a label stopped at the apostrophe in "the patient's own data" and silently truncated it, because prose contains quotes.
The tell is grammatical
If you can only say what a class is for by listing what it excludes, invert it.

Mechanical corollary: an unbounded substring is not a word. "ast" matched iodinated contrast; "alt" matched salt and altered; "ring " with a trailing space matched offering and suppressed a real finding. Bind every literal with \b, and keep stems as deliberate stems.

Guard where it lands

An assertion one boundary away from the decision is decoration. And a documented promise nobody enforces is worse than no promise.

Classify what a value is, wherever it is written — not what container it went into. A gate checking table names let "anaphylaxis to penicillin" land as a problem: visible in one view, invisible to the allergy query.

An unenforced documented promise is worse than an undocumented one

A type comment carried the guarantee "composed from our own words and a position — never the filename", enforced nowhere, and the client rendered the raw value on the one channel that is spoken aloud, unskippable, and invisible to visual review.

The comment is load-bearing in the wrong direction
It makes the code look audited. A reader opens the type, sees the guarantee, believes the invariant holds, and stops — so the documented promise actively suppresses the check that would have enforced it. Unenforced and undocumented is a hole. Unenforced and documented is a hole with a sign over it saying the floor is solid.

When a value crosses a trust boundary, the assertion has to live on the far side of it. Two verifiers did assert this invariant — both over values our own code composed from our own mock's data, so neither could ever see a server-supplied one. The tests were right and the population was wrong (ch. 26).

If a shared component states a fact about its caller, make the caller supply it

Closed key space
Record<Kind, Copy> with no index signature and no fallback. A seventh kind is a compile error — the compiler asks the question instead of a reviewer noticing.
Loose, with a fallback claim
Record<string, Copy> ?? fallback. A seventh kind silently inherits a sentence that is false about it.

The tell that finds these: a shared string sitting beside two or three maps keyed off the same discriminant. The maps got the treatment and the sentence did not, which is exactly why it drifted.

But the rule is not "tighten every map"
Tighten when the key space is a closed discriminant and a miss would render something false. Stay loose when the key space is open and a miss correctly renders nothing. A loose type is a bug only when the fallback is a claim.
29

Blast radius

A gate can cause the harm it exists to prevent. And caution compounds into uselessness — the failure nobody warns you about.

A gate can cause the harm it prevents

A banned-word check over device-claim verbs would fail the page that disclaims them — "does not diagnose, treat, cure, or prevent any disease" is the standard form and cannot be written without them. A literal check there pressures someone into softening the most load-bearing sentence in the product.

Word gates must be polarity-aware or scope-exempt. Prose about a hazard is not exempt from the hazard — the same shape took down every dev server on the project when a comment documenting a gitignore glob ended in */ and closed its own block comment early, while warning about a different way to break the build.

Never condition a penalty on the presence of an honest disclosure

A gate fired when an answer omitted a verified rule and admitted it could not verify something. The cheapest way to pass was to delete the "what I could not check" paragraph — and an answer that omitted the rule and hid the gap passed clean.

The rule
A gate whose easiest satisfaction is less honesty is worse than no gate. Related: never make a gate go red when someone improves something. A ratchet whose count may only fall should print the command to lower its own baseline, not fail on a decrease. A gate that punishes progress is a gate people switch off.

Caution compounds into uselessness

This does not look like a bug in any single place. Every individual refusal is defensible; stacked, they produce a product that cannot do the thing it exists to do. Because each one reads as responsible in isolation, code review will not catch it. The dial gets raised once per feature and never lowered.

A document-reading product told users "Nobody here has looked at these images. Interpreting a medical image is not something this system does." Seven separate sites — the prompt, a subagent brief, a tool description, an extractor — each independently cautious, all collectively describing a tool that refused its own purpose. Fixing it made the prompt smaller.

The test
Read your refusals end to end, as one document, and ask whether what remains is the product you set out to build. Then ask of each one: should this be a warning instead? A warning preserves the capability and informs the user; a refusal removes it. Most over-caution is a warning that got promoted.

Two structural defences

  • Keep genuine safety output exempt from every brevity, density and suppression rule — enforced structurally, so the tuning machinery cannot see it. Then aggressive tuning elsewhere is safe by construction, and you can tune hard. A carve-out you have to remember is not a carve-out.
  • Measure precision before shipping a gate that blocks. One citation gate, replayed over 259 real answers, flagged 179 pairs at 11% precision — and it was already live, already stripping real citations out of output users read. See ch. 30 → 08-measurement.md.

Altitude, a hard token ceiling, the caution dial, and why a guard you have never seen fire is a guard you have not tested.
